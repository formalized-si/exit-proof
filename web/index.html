EXIT STAGES FOR NEAR CONTRACTS · REGISTRY ON NEAR MAINNET

Can you always
get it back?

Before you, or your agent, deposit into a NEAR contract: who can change its code, who can move or freeze the funds, and is there a proof that you can always withdraw? Exit Proof gives every contract an exit stage. Each stage is defined by evidence that anyone can check again. The top stage takes a Lean theorem tied to the deployed code hash.

    01 · THE STAGES
    
  
    Four stages, each defined by evidence.
    
  
    A stage answers one question for a depositor: if I put money into this contract, what guarantees that I can get it back? The ladder follows the idea of L2BEAT's Stages for rollups. What is added here is the top rung: a stage is 2 only with a machine-checked exit theorem tied to the deployed code hash.
    
  
    
    
    StageMeaningEvidence
    
    
      
    2 Proven exitThe code cannot change, and a depositor can always withdraw by its own calls.No code-change path and no access key; an exit theorem registered on chain for the exact code hash by an accepted attestor; the account's state was made by this code: one deployment, or every deployment recorded by the proof.
    
      
    1 Exit windowThe code can change only after a visible delay, long enough to leave.The code runs the proved upgrade plugin (a certificate or a proof for its code hash), no other code-change method is found by name, and the plugin's delay is set. Names alone give stage 0.
    
      
    0 Keyholder trustThe code can change with no notice, or exits can be paused and deposits moved.The scanner names the path and how strongly it is guarded: a DAO vote, a multisig, another contract, several keys, one key.
    
      
    U UnprovenNo code-change path was found, and no exit theorem covers this account.Absence of evidence, stated as such: no theorem for the code hash, or the account has a key or a history the theorem does not cover.
    
        
  
    
  
    A report shows how strongly each power is guarded and never lists who holds it. The full rules.

    03 · WHAT IS PROVED
    
  
    A theorem about a model, tied to the deployed bytes.
    
  
    Three levels of evidence are kept apart everywhere. Proved is a Lean theorem about a model. Tested is the model run against the exact deployed wasm on nearcore's own runtime. Read is chain state or a contract's own answer.
    
  
    
    
    SubjectProved in LeanNot covered
    
    
      
    Core staking pool, the code of *.poolv1.nearA delegator can always unstake and withdraw. Nobody else lowers its balance.Storage staking. That the protocol returns the stake is an assumption.
    
      
    wNEAR, wrap.nearA holder can always unwrap, under an invariant of the state.The rest of the invariant on mainnet, and the code the account ran before 2021.
    
      
    Token ledger of NEAR Intents, intents.nearFor a standard token and for wNEAR the ledger never exceeds the holdings. Withdrawals settle exactly. A balance falls only in six ways, each with the checks the contract makes.The multi-token and NFT paths, the swap path (token_diff) and its fees, gas, the signature standards, a proof about the bytes.
    
      
    Token standard, near-contract-standards 5.29.0Supply is the sum of balances. Settlement refunds at most what was sent. Only the token settles.Other library versions: their verdicts come from runs.
    
      
    Upgrade plugin, near-plugins v0.5.1No deploy is accepted before a bound that is tight.Contracts that changed the plugin.
    
      
    Gated upgradesEvery code change installs code that had a certificate.The gate is as strong as the attestors it accepts.
    
        
  
    
  
    One statement, as Lean reads it
    
  
    theorem T1_ledger_covered (K : Cfg) (S : World) (h : Reach K S) :
    total S.L.bals ≤ bal S.c.accts K.me
    
  
    In every reachable state of the contract together with a standard token, the sum of the ledger balances is at most the token balance of the contract: with anything in flight, at any point of any interleaving, with any receipt failing. The Intents proof has the assumptions and what is not covered.

    05 · TOKENS
    
  
    Does this token behave as the standard?
    
  
    The proof of the Intents ledger holds for tokens that behave as the proved NEP-141 standard. The token check answers that for one token: the verdict for its code hash from runs of the deployed code, what is switched on right now, and whether its code can change.
    
  
    
    
    
    
      
      
    
    
    
    
      
      
      
    
    
  
    
  
    
  
    
    
    
    
    
  
    

    


    
  
    06 · ON NEAR MAINNET
    
  
    The certificates live in a contract nobody can change.
    
  
    registry.exitproof.near keeps the certificates by code hash. It has no access key and no upgrade method, and it holds nobody's funds. Each certificate pins a hash of the proof directory and names the command that re-checks the proof. The registry records who attests what; it does not check a proof on chain.

    WHAT THIS IS NOT
    
  
    A stage is evidence to weigh, not a guarantee.
    
  
      
    
    • Not a proof about the bytes. A theorem is about a Lean model. The tie to the deployed wasm is hash equality plus execution on random traces, and it is measured with one-line changes of the model.
      • 
    
    • Not checked on chain. A certificate is an attestor's statement with a command that re-checks it. The one attestor so far is an account with one key.
      • 
    
    • Not every risk. A stage is about exits. An oracle, the economic design and a bridge are outside it.
      • 
    
    • Not the finder of the 2026 incidents. The teams of those contracts found them, fixed them and published what happened.
